# KQ-007 — Implement Q001 state and theme APIs

## Outcome

Each child has an idempotently initialized KidQuest world whose presentation theme can change without changing gameplay state.

## Scope

1. Add service/repository boundaries for child world initialization and state reads.
2. Implement session-scoped APIs for current world state, available themes, and theme selection. There is no user authentication in this app: the active child is whatever the `math_sess` session selected through `GET /home/{child}`. Every KidQuest route derives the child from that server-side session, never from a request parameter or body, and returns `PROFILE_REQUIRED` when no child is selected.
3. Return logical entity IDs plus theme-resolved asset references without duplicating world entities.
4. Enforce profile isolation, optimistic versioning where needed, and consistent errors.
5. Add contract, idempotency, isolation, and theme-invariance tests.

## Deliverables

- Q001 world-state and theme APIs with schemas.
- Initialization service and API documentation.
- Automated tests.

## Acceptance criteria

- [x] First read creates exactly one valid starter world; later reads do not duplicate it.
- [x] Theme changes preserve coordinates, footprints, inventory, quest state, and balances.
- [x] No KidQuest route accepts a child identifier; a session bound to one child cannot read or modify the other child's world, and any child ID supplied in a request is ignored or rejected.
- [x] Invalid theme/state versions return documented non-destructive errors.
- [x] Legacy quiz behavior remains green.

## Verification

- Run API contract and full regression tests.
- Snapshot state before and after switching through all three themes and prove only presentation fields differ.

## Out of scope

- Challenge answering, rewards, placement UI, and final assets.
