# Database Operations

Operational reference for the SQLite database behind the quiz app and, later, KidQuest. It covers
runtime configuration, the Asia/Jakarta day boundary, backups, restore, the deployment runbook,
and backup retention.

## Runtime configuration

| Variable | Default | Effect |
| --- | --- | --- |
| `DB_PATH` | `math_app.sqlite3` (relative to the working directory); the Docker image sets `/data/kids-quiz/kids-quiz.sqlite3` | Database file, resolved each time a connection opens. |
| `APP_TIMEZONE` | `Asia/Jakarta` | Every day boundary: sessions, daily banks, statistics, quotas. An invalid IANA name stops startup. |
| `ADMIN_CLEAR_PASSWORD` | `masukaja` locally | Password for `POST /api/admin/clear`. **In production the app refuses to start** if it is unset, blank, or `masukaja`. |
| `SESSION_COOKIE_SECURE` | `true` in production, `false` locally | Adds `Secure` to the `math_sess` cookie. Accepts `true/false/1/0/yes/no/on/off`. |
| `SESSION_COOKIE_MAX_AGE` | `31536000` (365 days) | `Max-Age` of the session cookie, in seconds. |
| `SQLITE_BUSY_TIMEOUT_MS` | `5000` | How long a connection waits for a lock before failing. |
| `KIDQUEST_ENABLED` | `false` | Turns KidQuest on. When on, the content in `content/kidquest/` is validated at startup (invalid content stops the app) and the `/api/kidquest/*` routes are registered. When off, content is never read and the KidQuest routes do not exist (`/api/kidquest/*` returns the legacy API 404); legacy routes behave byte-for-byte the same either way. Turning it off is the rollback: KidQuest tables and player data stay in the database. |
| `KIDQUEST_PROFILE_ALLOWLIST` | empty | Comma-separated child IDs (`althafandra`, `alleia`) allowed into KidQuest during rollout. Empty admits nobody. A selected child outside the list gets HTTP 403 `KIDQUEST_DISABLED` from every KidQuest route. |
| `KIDQUEST_DAILY_ATTEMPT_LIMIT` | `20` | Accepted KidQuest answer attempts (correct or wrong) per child per `APP_TIMEZONE` (Jakarta) day, counted in `kidquest_daily_usage`. At the limit a new answer gets HTTP 429 `DAILY_CAP_REACHED` with the reset time; replays, world state, and theme changes still work. KidQuest attempts never change the legacy `child_daily` counters or `/api/stats`. |
| `KIDQUEST_PARENT_DASHBOARD_ENABLED` | `false` | Registers the adult-only KidQuest session, overview, and scoped-reset routes only when KidQuest is also enabled and both adult secrets below are valid. |
| `PARENT_PIN_HASH` | empty | PBKDF2 parent-PIN verifier generated by `PYTHONPATH=. .venv/bin/python scripts/hash_parent_pin.py`; never set a plaintext PIN. |
| `SESSION_SIGNING_KEY` | empty | HMAC key for adult-session cookies. Production requires at least 32 UTF-8 bytes. Generate a random deployment secret and do not reuse the PIN. |
| `KIDQUEST_ADULT_SESSION_MAX_AGE` | `900` | Adult-session lifetime and cookie `Max-Age`, in seconds. Must be a positive integer. |

Malformed values (for example `KIDQUEST_ENABLED=maybe`, an unknown child in the allowlist, or a
non-positive limit) raise `ConfigError` when the configuration is read, which stops both the
migration step and the app, like the other flags above. Fix the variable and redeploy.

**Production** means at least one of `RAILWAY_ENVIRONMENT`, `RAILWAY_ENVIRONMENT_NAME`, or
`RAILWAY_ENVIRONMENT_ID` is set. Railway injects these into deployed services. After the first
deploy, confirm that at least one is present with `railway ssh` then `env | grep RAILWAY_ENVIRONMENT`.
If none is present, neither the secure-cookie default nor the admin-secret check turns on. As a
safeguard, also set `SESSION_COOKIE_SECURE=true` explicitly in the Railway service variables.

The admin-secret check runs only when the application starts (`create_app`). The Docker build's
seed migration and the migration step in `docker-entrypoint.sh` never need the secret.

Every application connection is opened by `app/db/sqlite.py::db_conn`, which sets
`PRAGMA foreign_keys = ON`, `PRAGMA busy_timeout`, and the `sqlite3.Row` row factory. Multi-statement
writes use the unit of work:

```python
from app.db.sqlite import transaction

with transaction() as conn:          # BEGIN IMMEDIATE on one connection
    conn.execute("UPDATE ...")
    conn.execute("INSERT ...")       # commits together, or rolls back together on any exception
```

`BEGIN IMMEDIATE` takes the write lock at the start, so concurrent writers wait in turn, up to the
busy timeout, instead of failing halfway through.

**WAL is deferred.** The journal mode stays `DELETE`. Enable WAL only after backup/restore and the
Railway volume's behavior have been proven with `-wal`/`-shm` files present, and record that
decision here.

## Schema migrations

Migrations run automatically before the app starts (`scripts/migrate.py`). Each is additive and
safe to re-run.

| Version | Change |
| --- | --- |
| 1–7 | Legacy quiz: sessions, daily statistics, served questions, daily banks, unfinished questions. |
| 8 | KidQuest (additive, no legacy table touched): `kidquest_worlds`, `kidquest_buildings`, `kidquest_paths`, `kidquest_child_quests`, `kidquest_challenges`, `kidquest_attempts`, `kidquest_resource_balances`, `kidquest_resource_ledger`, `kidquest_blueprints`, `kidquest_idempotency`, `kidquest_daily_usage`. Take and verify a backup before deploying it (runbook steps 2–3). |
| 9 | KidQuest adult hardening (additive): append-only-by-policy `kidquest_audit_events` for scoped reset evidence and `kidquest_adult_session_revocations` so logout rejects a copied cookie across restarts. No legacy table is altered. |

## Adult session, scoped reset, and audit behavior

The adult cookie is HMAC-signed, `HttpOnly`, `SameSite=Strict`, `Path=/`, and `Secure` whenever
`SESSION_COOKIE_SECURE` is true. The signed payload has a version, expiry, and random nonce. Expiry
is checked against `app/clock.py`. Logout records the nonce digest in
`kidquest_adult_session_revocations` before clearing the cookie; replaying a copied token is then
rejected. Neither the token nor its nonce is logged. Expired revocation rows may be removed by a
future maintenance task after their `expires_at`; the current household-pilot implementation keeps
them because they are small and security-sensitive.

Adult reset confirmations are deliberately different: `legacy_history` = `HAPUS-KUIS`,
`kidquest_progress` = `HAPUS-DUNIA`, and `all_child_data` = `HAPUS-SEMUA`. The operation is one
`BEGIN IMMEDIATE` transaction, including its audit insert. Reset idempotency is stored in the audit
event using a SHA-256 digest of the `Idempotency-Key`, because a KidQuest-progress reset must delete
the child's ordinary `kidquest_idempotency` rows. The raw key and confirmation text are not stored.

- `legacy_history` deletes that child from `child_daily`, `served_questions`,
  `daily_question_banks`, and `session_current_questions`. Shared `sessions` rows and counters stay;
  only active-question columns are cleared on sessions currently selecting that child. Sessions
  selecting the other child are unchanged.
- `kidquest_progress` deletes that child, in FK-safe order, from worlds, buildings, paths, quests,
  challenges, attempts, resource balances/ledger, blueprints, daily usage, and ordinary KidQuest
  idempotency. The next `GET /api/kidquest/state` lazily creates a fresh Q001-available world.
- `all_child_data` applies both scopes in the same transaction.

`kidquest_audit_events` is excluded from every reset and from legacy `/api/admin/clear`. It contains
the stable child ID, scope, event type, timestamps, response/deletion counts, and request/key hashes;
it contains no child name, answer, PIN, cookie, or raw idempotency key. Application code exposes no
update/delete operation for this table.

## Day boundary and the UTC → Asia/Jakarta cutover

### Before and after

- **Before KQ-002:** the legacy day came from `date.today()`, which follows the container's local
  timezone. The `python:3.12-slim` image and `railway.toml` set no `TZ`, so production is expected
  to run in UTC. The legacy day therefore rolled over at **07:00 WIB** (00:00 UTC). The live
  container's timezone has not been observed directly; confirm with `railway ssh` then `date +%Z`.
- **After KQ-002:** every day boundary uses `APP_TIMEZONE` (default `Asia/Jakarta`) through
  `app/clock.py`, whatever the container's `TZ` is. The day rolls over at **00:00 WIB**.

### Effect on existing data

- Existing `child_daily` rows are keyed by **UTC day**. The row for date *D* holds activity from
  07:00 WIB on *D* to 07:00 WIB on *D+1*. **Historical rows are not rewritten.**
- `sessions.created_at` and `/api/stats` `recap7.generated_at` keep their format
  (`YYYY-MM-DDTHH:MM:SS`, no offset) but are now Jakarta wall time instead of container-local time.
- `served_questions` and `daily_question_banks` only ever keep the current day. They are rebuilt
  automatically on the first question request of the new day.

### The cutover day

Let *T* be the moment the new code starts serving.

| Deploy time *T* (WIB) | Effect |
| --- | --- |
| 07:00–23:59 on day *D* (UTC day and Jakarta day are both *D*) | No immediate reset. Row *D* holds 07:00 → 24:00 WIB on *D*: **17 hours**. Row *D+1* is a normal 24-hour Jakarta day. |
| 00:00–06:59 on day *D+1* (UTC day still *D*, Jakarta day already *D+1*) | The next request from each session resets it as at a normal midnight. A question that was on screen is rejected once with "Soal tidak sinkron. Klik Next lagi.", and day *D*'s bank is replaced. Row *D* holds 07:00 WIB *D* → *T*. Row *D+1* holds *T* → 24:00 WIB *D+1*. Each is **17–24 hours**. |

So the cutover **never makes a day longer than 24 hours**. One legacy day shrinks to as few as 17
hours. The daily quota (400 units) still applies per row, so the short day just ends earlier.

**Rollback warning (31 hours):** if the code is rolled back to a pre-KQ-002 (UTC-keyed) build after
running on Jakarta days, the opposite happens. Row *D* holds Jakarta-keyed activity from 00:00 WIB
plus UTC-keyed activity until 07:00 WIB on *D+1*: **up to 31 hours**. Prefer rolling forward. If you
must roll back, note the day in the cutover log.

> The KQ-002 task packet says the cutover day "may contain up to 31 hours of activity". For the
> UTC → Jakarta direction the day gets shorter (17–24 hours); 31 hours applies only to the rollback
> direction described above.

**Recommended deploy window:** 07:00–23:00 WIB, so children in the middle of a quiz are not reset.

### Cutover log

Fill this in when the cutover is deployed to production.

| Field | Value |
| --- | --- |
| Deployment time (WIB) | _not yet deployed_ |
| Container `TZ` observed before deploy (`date +%Z`) | _pending_ |
| Last UTC-keyed `child_daily` day | _pending_ |
| First Jakarta-keyed `child_daily` day | _pending_ |
| Short day and its hours | _pending_ |

## Backups

`scripts/backup_db.py` copies the live database with SQLite's online backup API
(`sqlite3.Connection.backup()`), then runs `PRAGMA integrity_check` and `PRAGMA foreign_key_check`
on the copy. It opens the source read-only, never overwrites an existing file, and never deletes
backups.

```bash
# In the container (DB_PATH and PYTHONPATH are already set by the image):
python /app/scripts/backup_db.py
# Locally, from the repository root:
PYTHONPATH=. python scripts/backup_db.py --source path/to/db.sqlite3 --output path/to/backup.sqlite3
```

By default it writes `<db dir>/backups/<db name>-YYYYMMDD-HHMMSS.sqlite3`, with the time in
`APP_TIMEZONE`. In production that is `/data/kids-quiz/backups/kids-quiz-…sqlite3`, on the same
Railway volume. It prints the backup path, `integrity_check: ok`, the schema version, and the row
count per table. It exits non-zero if the source is missing, the output exists, or the copy fails
its checks. A write that is still uncommitted while the backup runs is not included: the backup
always reflects the last committed state.

## Verify and restore

`scripts/verify_backup.py` checks integrity and foreign keys, and confirms the file has a
`schema_migrations` table. It then restores the backup into a fresh location and proves the
restored copy matches the backup exactly (a SHA-256 over every table's schema and rows).

```bash
# Verify, with a throw-away test restore in a temporary directory:
python /app/scripts/verify_backup.py /data/kids-quiz/backups/kids-quiz-20261121-100000.sqlite3

# Also prove the backup equals the live database (valid only if nothing was written since the backup):
python /app/scripts/verify_backup.py <backup> --compare-with "$DB_PATH"

# Restore into a new file and keep it (refuses to overwrite):
python /app/scripts/verify_backup.py <backup> --restore-to "$DB_PATH.restored"
```

It prints `Backup verified`, `integrity_check: ok`, the schema version, row counts,
`restore test: ok`, and the digest, and exits non-zero on any failure.

## Deployment runbook

Sequence: **backup → verify → migrate → deploy → smoke test → rollback if needed.** Deploy between
07:00 and 23:00 WIB.

1. **Pre-flight.** In the Railway service variables, confirm `ADMIN_CLEAR_PASSWORD` is set to a
   strong, non-default secret. Without it the new deployment refuses to start and fails its
   `/health` check. Railway then keeps serving the previous deployment, but the release is blocked.
   Also set `SESSION_COOKIE_SECURE=true` explicitly.
2. **Backup.** `railway ssh`, then `python /app/scripts/backup_db.py`. Record the printed backup
   path and row counts.
3. **Verify.** `python /app/scripts/verify_backup.py <backup path>`. Do not continue unless it
   prints `Backup verified` and `restore test: ok`. If an off-volume copy is required, use a
   transfer method already proven for this Railway project; this runbook has not tested one.
4. **Migrate.** Migrations run automatically. `docker-entrypoint.sh` copies the seed database if
   the volume is empty, then runs `scripts/migrate.py` before Uvicorn starts. Migrations are
   additive and idempotent; the deploy log shows `Applied SQLite migrations: …` or
   `SQLite schema is up to date.`
5. **Deploy.** Push the reviewed commit (or `railway up`). Railway builds the Dockerfile and waits
   for `/health`.
6. **Smoke test.**
   - `GET /health` returns `{"ok": true}`.
   - `GET /home` renders. Choose a profile, open `/quiz/math`, answer one question, and check that
     the counter increases.
   - `GET /api/stats`: `day` is today's **Jakarta** date and `recap7` lists both children.
   - In the browser's dev tools, the `math_sess` cookie has `Secure`, `HttpOnly`, `SameSite=Lax`,
     `Path=/`, and a one-year expiry.
   - The deploy log has no `ConfigError`.
   - For the first KQ-002 deploy, fill in the cutover log above.
7. **Rollback.**
   - **Code:** redeploy the previous deployment from the Railway dashboard. Migrations so far are
     additive, so older code ignores newer tables. Rolling back past KQ-002 brings back the UTC day
     boundary (see the 31-hour warning).
   - **Data** (only if data is damaged; it loses every write since the backup):
     1. `python /app/scripts/verify_backup.py <backup> --restore-to "$DB_PATH.restored"`
     2. `mv "$DB_PATH" "$DB_PATH.before-restore-$(date +%Y%m%d-%H%M%S)"`
     3. `mv "$DB_PATH.restored" "$DB_PATH"`
     4. Restart the service immediately, so no request keeps writing to the moved file.
     5. Repeat the smoke test. Keep the `before-restore` file until the restore is confirmed.

## Backup retention (manual)

Nothing deletes backups automatically. Review them at least monthly and before each migration:

1. List them and check free space: `ls -lh /data/kids-quiz/backups` and `df -h /data`.
2. Always keep:
   - the newest **verified** backup;
   - the pre-deploy backups of the **last three** deployments;
   - every backup taken **before a migration that adds tables** (for example before KidQuest
     Migration 8), until that release has run without data issues for **30 days**.
3. Before deleting anything, run `verify_backup.py` on the newest backup you are keeping and make
   sure it passes.
4. Delete older files one at a time with `rm <file>`. Never use wildcards in the backups folder.
5. If the volume passes 80% use, free space by following steps 2–4, or enlarge the volume. Do
   not skip pre-deploy backups.
